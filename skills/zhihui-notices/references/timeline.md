# 查询近期安排并生成时间轴

## 查询与核对

1. 优先调用 `list_events`，按返回的 `today` 和 `timeZone` 明确窗口，默认今天到今天加六天。用户指定本周、下周或其他范围时按要求计算并写出起止日期。查询全部已结构化时间用 `type: all, recordType: all, kind: all`，持续分页；只查课程可用 recordType course，其他事件用 schedule，二者都覆盖两路记录但不含任务。周期课表及同一事件中各时间项按实际发生日期展示，不得把多时间点压成一个规则。面板按记录显示卡片，时间轴按发生展示，两者数量可以不同；改分类不改变展开。该工具已汇总两路事件和任务实例，不能再把 `list_tasks` 的同一计划重复添加。工具尚未提供时，退回下面的事件查询，并说明不包含未读取的个人日程或任务。
2. 已录入安排不需要遍历所有事件才能列出。需要事件原文、材料要求、时间依据缺失或要求完整核对尚未结构化的事件时，再实时 `list_notices` 并 `get_notice`。`deadline` 筛选不会检索 `events`；完整事件核对需不带日期过滤分页读取正文，不能仅凭标题或 240 字摘录排除某条事件。数据量很大而无法全部核对时，明确已扫描范围和尚未核对的数量，不用“没有安排”代替“没有查完”。不要据旧事件补造未经导入的用户课表。
3. 有原文时按原文核对，补充正文中未结构化的时间时明确它们仅是本次提取、未保存；空数组也可能表示用户尚未设置时间，不能补造。可提取报名截止、提交截止、活动等多个独立事项。`deadline` 作为旧截止字段补充展示，同一事件已有同日期的截止事项时不重复；活动日不能用它代替。notices 实例保留真实 `noticeId`，个人日程和任务使用真实来源编号；记录可能没有原文，此时如实引用本轮返回的 date/time/recurrence 字段作为已保存时间依据，不冒充原文。时分未知就留空，无日期记录不混入确定的时间节点。
   活动区间保留真实开始 `date/time` 和结束 `endDate/endTime`；与窗口有交集就包含，开始早于窗口时标明“进行中”，不能把窗口首日称为实际开始日。结束日期或时间未知就留空，不能按假定时长推算。原有只含时间点的输入仍可使用，不必拆成重复的开始和结束事项。
4. `publishedAt` 是发布日，`deadline` 是截止日，二者都不能直接替代活动日。原文相对日期要依据原始发布时间；缺年份、含糊的“下周”、冲突日期无法可靠确定时，放入“时间待确认”。注明这部分是否落在查询窗口尚待确认，不把它们算入确定的近期安排。
5. 按日期、明确时分排序。没有时分的同日事项标为“时间未注明”，截止节点标为“截止”，来源未知显示“来源未注明”。按 participation 明确区分“资料信息”（reference）与“我的安排”（planned）；有日期进入时间表不等于已报名，reference 不作为忙闲硬约束。不得以 sourceType notice 判定候选、event 判定承诺。任务完成状态以本次工具结果为准。没有确定结果时显示空态和实际检查范围；仅查结构化时间时注明“尚未逐条核对未结构化事件正文”。

## 本地 HTML 时间轴

脚本需要 Node.js 18 或以上，无 npm 依赖、网络请求和凭据。用本轮工具结果建立 JSON；以下为字段格式，日期、编号、标题都要替换为实际结果：

```json
{
  "title": "未来七天的事件安排",
  "today": "2026-10-18",
  "timeZone": "Asia/Shanghai",
  "from": "2026-10-18",
  "to": "2026-10-24",
  "coverage": "已读取当前账号全部 8 条事件的完整原文；这是查询时的快照。",
  "events": [{
    "date": "2026-10-20",
    "time": "14:00",
    "endDate": "2026-10-20",
    "endTime": "16:00",
    "kind": "event",
    "title": "设计讲座",
    "noticeId": "实际事件编号",
    "sourceName": "学生发展中心",
    "sourceUrl": "",
    "location": "图书馆报告厅",
    "detail": "按原文核对的参与方式或材料要求。",
    "evidence": "原文写明：2026年10月20日14:00至16:00在图书馆报告厅举行。"
  }],
  "undated": [{
    "title": "时间尚待确定的事件标题",
    "noticeId": "实际事件编号",
    "reason": "原文仅写下周，缺少可靠发布时间，是否在本窗口内待确认。"
  }]
}
```

`time` 可留空，其余来源和地点可省略；`events`、`undated` 可为空数组。每个确定事项必须有有效日期、标题、类型、真实来源编号和时间依据。事件继续用 `noticeId`；个人日程或任务可不填 `noticeId`，改用 `reference: {"type":"event","id":"实际日程编号"}` 或 `reference: {"type":"task","id":"实际任务编号"}`，待确认项也支持该格式。有真实关联事件时两种编号都可保留。不要将 `list_events` 的临时实例标识误当成可更新的周期编号。

时间点需落在窗口内，已知区间需与窗口相交。`endDate`、`endTime` 可省略；结束时分必须有开始时分且结束晚于开始。`kind` 使用 `event`（活动）或 `deadline`（截止），脚本也兼容原有“活动开始”“报名截止”等类型；截止不能有结束范围。范围事件只占一个事项，页面保留实际起止。

这些是排版脚本的输入，不能把 `reference` 等排版字段传入 MCP。脚本要求每项有 `evidence`：有原文就用原文证据，个人日程可用已保存的 `sourceText/notes`；没有原文时可如实写“本轮 list_events 返回 date=…、time=…、recurrence=…”，任务可引用返回的计划或截止字段，不冒充原文或实际用时。不要为生成图强迫用户补写不存在的来源。在 detail 中按实际 participation 写“资料信息”或“纳入我的安排”，不传脚本尚未支持的新字段。`coverage` 必须描述真实覆盖范围，不照抄示例条数。没有查询到某项就不添加，不能把示例当作事件库或课表内容。

在实际 skill 目录下执行，输入和输出路径按用户工作区选择：

```text
node scripts/render-timeline.mjs 实际输入.json 实际输出.html
```

脚本只把已核对信息排版，不会调用 MCP 或替 Agent 提取日期。打开生成的 HTML 检查日期分组、类型、来源编号和空态，再向用户返回本地文件链接或客户端支持的 HTML 附件。文件只在本地保存；不要为展示而擅自发布网页。它是静态快照，知会内容变化后需要重新生成。

## 无文件执行能力时

使用聊天时间轴，例如：

```text
10 月 20 日
  14:00  活动开始｜设计讲座
         地点：图书馆报告厅 · 事件编号：实际编号
10 月 23 日
  时间未注明  截止｜设计竞赛报名
              来源：实际来源 · 事件编号：实际编号
```

少量结果直接回答即可，不为了生成图而安装运行环境。客户端原生支持图表时可用其能力，但仍保留日期类型、编号和覆盖说明。
