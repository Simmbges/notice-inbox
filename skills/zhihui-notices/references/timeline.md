# 从通知生成近期安排

## 查询与核对

1. 调用 `list_notices` 获得服务端 `today` 和 `timeZone`，默认范围为今天到今天加六天。用户指定本周、下周或其他范围时按要求计算，并在回复中写出起止日期。
2. 只查截止事项时用截止筛选。一般“日程安排”不等于截止事项：不带日期过滤分页查询，并用 `get_notice` 读取原文，才能包含没有截止日期的讲座、会议、课程等。完整核对需要读取所覆盖通知的完整正文，不能仅凭标题或 240 字摘录排除某条通知。数据量很大而无法全部核对时，明确写已扫描范围、尚有多少未读；可与用户缩小范围，不用“没有安排”代替“没有查完”。
3. 从每条原文提取多个独立时间点，例如报名截止、提交截止、活动开始、活动结束。每个节点保留同一真实 `noticeId`、日期证据 `evidence`，时分只有原文明示时才填。持续活动可用开始和结束节点表达，不能改成新的截止日期。跨越查询窗口的持续活动，在范围内以“进行中”节点表达，并在证据和说明中保留真实起止日期，不能称该节点日期是开始日。
4. `publishedAt` 是发布日，`deadline` 是截止日，二者都不能直接替代活动日。原文相对日期要依据原始发布时间；缺年份、含糊的“下周”、冲突日期无法可靠确定时，放入“时间待确认”。注明这部分是否落在查询窗口尚待确认，不把它们算入确定的近期安排。
5. 按日期、明确时分排序。没有时分的同日事项标为“时间未注明”，截止节点标为“截止”，来源未知显示“来源未注明”。通知本身不证明用户已报名、已完成或必须参加；用“通知中提到的安排”表述。没有确定结果时显示空态和实际检查范围。

## 本地 HTML 时间轴

脚本需要 Node.js 18 或以上，无 npm 依赖、网络请求和凭据。用本轮工具结果建立 JSON；以下为字段格式，日期、编号、标题都要替换为实际结果：

```json
{
  "title": "未来七天的通知安排",
  "today": "2026-10-18",
  "timeZone": "Asia/Shanghai",
  "from": "2026-10-18",
  "to": "2026-10-24",
  "coverage": "已读取当前账号全部 8 条通知的完整原文；这是查询时的快照。",
  "events": [{
    "date": "2026-10-20",
    "time": "14:00",
    "kind": "活动开始",
    "title": "设计讲座",
    "noticeId": "实际通知编号",
    "sourceName": "学生发展中心",
    "sourceUrl": "",
    "location": "图书馆报告厅",
    "detail": "按原文核对的参与方式或材料要求。",
    "evidence": "原文写明：2026年10月20日14:00在图书馆报告厅举行。"
  }],
  "undated": [{
    "title": "时间尚待确定的通知标题",
    "noticeId": "实际通知编号",
    "reason": "原文仅写下周，缺少可靠发布时间，是否在本窗口内待确认。"
  }]
}
```

`time` 可留空，其余来源和地点可省略；`events`、`undated` 可为空数组。每个确定节点必须有有效范围内日期、标题、类型、编号和证据。`coverage` 必须描述真实覆盖范围；不要照抄示例条数。没有查询到某项就不要添加，不能把这里的示例当作通知库内容。

在实际 skill 目录下执行，输入和输出路径按用户工作区选择：

```text
node scripts/render-timeline.mjs 实际输入.json 实际输出.html
```

脚本只把已核对信息排版，不会调用 MCP 或替 Agent 提取日期。打开生成的 HTML 检查日期分组、类型、来源编号和空态，再向用户返回本地文件链接或客户端支持的 HTML 附件。文件只在本地保存；不要为展示而擅自发布网页。它是静态快照，知会内容变化后需要重新生成。

## 无文件执行能力时

使用聊天时间轴，例如：

```text
10 月 20 日
  14:00  活动开始｜设计讲座
         地点：图书馆报告厅 · 通知编号：实际编号
10 月 23 日
  时间未注明  截止｜设计竞赛报名
              来源：实际来源 · 通知编号：实际编号
```

少量结果直接回答即可，不为了生成图而安装运行环境。客户端原生支持图表时可用其能力，但仍保留日期类型、编号和覆盖说明。
