# 从事件和个人约束形成计划

用于任务拆解、今日或每周计划、优先级、冲突分析和自然反馈后的调整。工具参数见 [MCP 约定](mcp.md)；旧连接没有管理工具时仍可给建议，但不能声称已保存。

## 依据与范围

制定或移动计划时，按 [日程与时间轴](timeline.md) 实时查询范围内的日程实例，并读取 `list_tasks` 和 `get_preferences`，注明日期范围和覆盖缺口。仅标记完成、重开、取消或调整任务优先级时，先读相关任务确认对象和版本即可，不必额外读取课表与偏好。涉及事件材料和详细要求时再读取 `get_notice`；只规划个人任务不必写事件。日期依据使用 MCP 返回的 `today`、`timeZone`；没有相应查询时使用当前已知日期和时区，不猜测所在地。

输出中让用户能分清：

- **资料信息**：`participation: reference` 的事件或课程，仅作资料和候选机会；有日期会进入时间表，但不自动占用个人空闲。原文明示的材料、地点和适用对象按真实来源核对，没有原文或来源就说明未附，不编造依据。
- **我的安排**：`participation: planned` 的事件、课程以及已保存的个人任务，或本次明确说过要纳入计划的活动。引用对应真实编号；只说“想参加、考虑一下”仍是候选。`sourceType` 只区分存储来源，notice 记录也可能是已确认安排，event 记录也可能仅供参考。用户没有说过或工具没有返回的完成情况不补全。
- **建议**：拆解步骤、预计用时、缓冲和建议时段，明确为估计或建议，不能混入事件事实。用户实际确认后才称为承诺。

## 形成可执行建议

结合已存 `dayStart`、`dayEnd`、`dailyCapacityMinutes`、`bufferMinutes` 和偏好备注，再结合用户给出的空闲时段、课程、工作、睡眠、出行、优先级及截止安排。首次返回的系统默认偏好要标为排程假设，不能当作用户已确认。明确的新要求优先于旧偏好；仅当用户要求记住或明确表达持续偏好时，使用 `update_preferences` 保存。临时说“今天只有半小时”只影响今天，不能擅自变成长期容量。只追问会改变排程的关键缺口；缺少可用时间或工作量时先给顺序和明确标为估计的用时，不据“未提供安排”推断全天空闲。

把目标拆成能着手执行的步骤，例如“确认报名资格 → 准备材料 → 提交 → 核对回执”。步骤必须与原文要求或用户目标有关，材料未知就写待核对；估时和提前量属于建议。先放用户确认的固定安排，再为相关截止事项向前安排准备、提交和检查；当天截止且时分未知时提醒核对具体时刻，不能默认当天 23:59。

今日计划给出当前可执行的下一步、预计用时、建议时段或先后顺序、完成判断和关联截止。每周计划按具体日期列出固定承诺、可选活动、准备任务和缓冲；本周已过日期作为回顾背景，不能安排未来执行。少量任务用紧凑表格即可，不为简单计划生成复杂日历。

## 时间约束和冲突

- 仅 planned 的已确认课程或安排可作为个人固定时间约束；reference 即使有周期、属于课程或已收藏，也不能自动排成用户必到。两项已纳入安排的明确时间区间重叠，才称为已知时间冲突。端点相接是否来得及，还取决于地点、交通及缓冲。
- 事件候选活动与承诺重叠，标为“若参加则冲突”；两项候选活动重叠，给出选择，不替用户决定参加。
- 只有开始时刻、没有结束时刻，或缺少日期/时分，说明无法确认重叠；同一天不等于必然冲突，也不能保证无冲突。
- 根据用户给出的可用时长与估时发现容量不足时，说明计算假设，建议缩减范围、提前或调整优先级。不要静默移动原文截止日或已确认安排。

## 保存任务和自然反馈

用户明确说“我要完成这项”“加入待办”“把报告安排到周三”即已提供任务或计划授权，使用 `create_task` 或 `update_task` 落库，不重复询问是否保存。仅让 Agent 给方案、列备选机会或说“考虑参加”不等于创建任务。不要把自己的每条拆解建议都自动变成持久任务；用户要求把目标拆成待办时，再保存相应步骤。

新事件可经 `import_notices` 保存为 planned；课表和已有个人日程沿用原工具，更新 participation 需要对应工具实际支持。用户要将已有 notices 资料改为“纳入我的安排”时，`update_notice_events` 只能改时间项，不能改根参与状态，需说明在面板编辑；不能重导副本或通过单独新增任务假装已修改原事件。没有日期仍可保存资料，不能虚构时间来凑排程。

- 创建前实时查看相关任务，避免因同义表述重复创建；是否新增、去重及编号以 `create_task` 返回为准。关联事件只填真实 `noticeId`，个人任务无需伪造事件编号。
- `dueDate` 只放用户目标或关联事件明确的截止日；`estimatedMinutes` 是预计用时。`plannedDate`、`plannedStartTime`、`plannedEndTime` 是计划，不能冒充实际投入或原文截止。建议估时明确标注，缺少结束时分时不要默认填写；用户授权排程后可按公开估时保存。
- “报告做完了”可更新为 `done`；“还没做完／重新开始”按上下文更新为 `todo` 或 `in_progress`；“不做了”使用 `cancelled`，不删除；“周三再做／优先处理这个”更新对应计划或优先级。用户说已完成不代表此前估时就是实际用时。
- 修改前从本轮查询获取真实编号和 `version`，提交 `expectedVersion`；不能凭标题猜编号。多条同名任务、模糊的“那个”或调课范围不清时，只问对象或范围这一关键缺口。版本冲突先重新读取并比较，不能盲目覆盖并发修改。
- “今天没做完，挪到明天”只改变明确涉及的任务；先检查明日固定日程与容量。超出容量就提出可执行的取舍，不静默挤占课程、移动原文截止或修改其他任务。未承诺的替代建议继续标为建议。

成功后简要报告保存或更新的任务、编号、状态和日期，区分已执行的更新与尚未采纳的建议。工具失败就如实说明哪些未保存。保存日程和任务不会设置提醒、订阅推送或创建外部日历事件，不能说“届时会提醒”。
